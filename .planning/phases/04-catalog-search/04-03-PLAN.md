**EXACT SQL pattern (copy verbatim from TechArch — do not modify):**
```sql
SELECT
  ir.*,
  ts_rank(ir.search_vector, plainto_tsquery('english', $1)) AS relevance_score,
  ts_headline('english', ir.problem_statement, plainto_tsquery('english', $1),
              'MaxWords=35, MinWords=15, ShortWord=3, HighlightAll=false,
               MaxFragments=1, FragmentDelimiter="..."') AS highlight
FROM innovation_records ir
WHERE ir.search_vector @@ plainto_tsquery('english', $1)
  AND ir.publication_state = 'PUBLISHED'
ORDER BY relevance_score DESC, ir.published_at DESC
LIMIT $2 OFFSET $3;
```

Implement in SearchService using `db.raw()` with parameterized bindings (never string interpolation):
```typescript
const result = await db.raw(`
  SELECT
    ir.id AS record_id,
    ir.title, ir.short_summary, ir.maturity_level, ir.review_status,
    ir.source_type, ir.reuse_potential, ir.contributing_office, ir.published_at,
    ts_rank(ir.search_vector, plainto_tsquery('english', ?)) AS relevance_score,
    ts_headline('english', ir.problem_statement, plainto_tsquery('english', ?),
                'MaxWords=35, MinWords=15, ShortWord=3, HighlightAll=false, MaxFragments=1, FragmentDelimiter="..."') AS highlight
  FROM innovation_records ir
  WHERE ir.search_vector @@ plainto_tsquery('english', ?)
    AND ir.publication_state = ?
  ORDER BY relevance_score DESC, ir.published_at DESC
  LIMIT ? OFFSET ?
`, [sanitizedQ, sanitizedQ, sanitizedQ, pubState, safePageSize, offset]);
```

Note: plainto_tsquery receives the sanitized query string three times (for ts_rank, ts_headline, and the WHERE clause). All three bindings are parameterized.

**Additional filter application (AND conditions appended after the base WHERE):**
When filter params are provided alongside `q`, apply them by wrapping the raw query in a CTE or by building the query with additional AND clauses. Simplest approach: add AND clauses to the WHERE before LIMIT:
```sql
  AND ir.maturity_level = ANY(?) -- maturity_level filter array
  AND ir.review_status = ANY(?)  -- review_status filter array
  -- etc.
```
OR: Use a subquery approach where the FTS query is the inner query and Knex filter builder wraps it.

**Query sanitization (in SearchService.sanitizeQuery):**
```typescript
private sanitizeQuery(q: string): string {
  // Strip HTML tags (prevent XSS and tsquery injection via HTML-like input)
  return q.replace(/<[^>]*>/g, '').trim();
}
```
Note: plainto_tsquery safely handles special characters (it is NOT websearch_to_tsquery). plainto_tsquery treats all input as plain words/phrases — ampersands, quotes, etc. are converted to lexemes safely. The only required sanitization is HTML tag stripping.

**Scope filtering:**
- PUBLIC: AND ir.publication_state = 'PUBLISHED' (hardcoded constant, never from user input)
- CURATOR: AND ir.publication_state IN ('DRAFT','REVIEW','PUBLISHED','SUPERSEDED','ARCHIVED')

**SearchResultCard shape:**
CatalogCard fields + highlight + relevance_score. After fetching FTS rows, batch-load tags and engagement_options by record_id exactly as CatalogService does. Reuse the same label maps (maturityLabels, reviewStatusLabels) — extract to src/constants/record-labels.ts if not done in 04-01.

**Total count for pagination:** Run a separate COUNT query:

```sql
SELECT COUNT(*) AS total FROM innovation_records ir
WHERE ir.search_vector @@ plainto_tsquery('english', ?)
  AND ir.publication_state = 'PUBLISHED'
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | Untrusted `q` search query string and filter arrays crossing into FTS query builder |
| db→API | innovation_records rows (including stored text fields) crossing from DB into JSON search results |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-06 | Tampering (SQL injection) | GET /api/v1/search — `q` param crosses into plainto_tsquery SQL call | mitigate | `src/services/search.ts::search` uses `db.raw()` with parameterized `?` bindings — `sanitizedQ` is NEVER string-interpolated into the SQL string; `plainto_tsquery('english', ?)` receives q as a binding, making injection impossible |
| T-04-07 | Tampering (XSS via search input) | `q` param contains HTML tags that could be reflected back in search results or highlight snippets | mitigate | `src/services/search.ts::sanitizeQuery` strips all HTML tags via `q.replace(/<[^>]*>/g, '')` BEFORE passing to plainto_tsquery; ts_headline output is HTML (PostgreSQL renders `<b>` tags) — route handler must JSON-encode highlight (already safe in JSON), and EJS template (04-04) must escape highlight field rendering |
| T-04-08 | Denial of service | GET /api/v1/search — unbounded query length causes PostgreSQL FTS overhead | mitigate | `src/routes/api/search.ts` enforces 500-char limit on raw `q` before calling service; `src/services/search.ts` also enforces limit — returns 400 QUERY_TOO_LONG; prevents tsquery parsing of pathologically long strings |
| T-04-09 | Information disclosure | GET /api/v1/search — DRAFT/SUPERSEDED/ARCHIVED records returned to PUBLIC caller | mitigate | `src/services/search.ts::search` hardcodes `AND ir.publication_state = 'PUBLISHED'` as a parameterized constant in the WHERE clause for PUBLIC scope — never derived from user input; non-PUBLISHED records never appear in FTS results |
| T-04-10 | Information disclosure | ts_headline snippet from problem_statement could expose content from non-matching records if scope filter is misapplied | mitigate | ts_headline is generated within the same parameterized query that enforces `publication_state = 'PUBLISHED'` — the WHERE clause and the SELECT expressions operate on the same filtered row set; no cross-row leakage is possible |
</threat_model>
