**Page structure — 3-tab layout:**

Tab 1: Core Fields
- title (text, required)
- problem_statement (textarea, required, min 50 chars)
- what_was_explored (textarea, required, min 50 chars)
- outcome_summary (textarea, required, min 50 chars)
- short_summary (textarea, optional, max 280 chars — show char counter)
- reuse_guidance (textarea, optional)
- maturity_level (select — EXACT option values and labels, in this order):
  - value="IDEA" label="Idea"
  - value="EXPERIMENT_POC" label="Experiment / POC"
  - value="PROTOTYPE_PILOT" label="Prototype / Pilot"
  - value="PRODUCTION_VALIDATED" label="Production / Validated Pattern"
  - value="ARCHIVED" label="Archived"
- review_status (select — EXACT option values and labels, in this order):
  - value="SUBMITTED" label="Submitted"
  - value="CURATED" label="Curated"
  - value="TECHNICALLY_REVIEWED" label="Technically Reviewed"
  - value="SECURITY_REVIEWED" label="Security Reviewed"
  - value="POLICY_REVIEWED" label="Policy Reviewed"
  - value="VALIDATED_FOR_REUSE" label="Validated for Reuse"
  - value="SUPERSEDED_RETIRED" label="Superseded / Retired"
- reuse_potential (select: HIGH | MEDIUM | LOW)
- source_type (select: I_AND_R | COMMUNITY)
- owner_name (text, required)
- owner_office (text, required)
- contributing_office (text, required)
- contributor_attribution (text, optional)
- last_reviewed_date (date input)
- default_perspective (select: EXECUTIVE | TECHNICAL)

Tab 2: Perspectives
- executive_perspective_text (textarea)
- executive_recommendation (textarea)
- technical_perspective_text (textarea)
- security_findings (textarea)
- performance_findings (textarea)

Tab 3: Artifacts & Metadata
- Key Findings: dynamic list — each finding has finding_text (textarea) + display_order (hidden); Add Finding button appends a new row; Remove button on each row
- Artifact Links: dynamic list — each link has label (text), url (text, must start https://), artifact_type (select: DOCUMENT|CODE_REPOSITORY|VIDEO|DIAGRAM|OTHER), display_order (hidden); Add Artifact Link button appends row
- Tags: dynamic list — each tag has tag_type (select: MISSION_AREA|TECHNOLOGY_AREA), tag_value (text); Add Tag button appends row
- Engagement Options: checkboxes for REQUEST_DEMO | REQUEST_ADOPTION_DISCUSSION | REQUEST_TECHNICAL_GUIDANCE | REQUEST_BRIEFING

**Publication state controls** (shown on edit.html only, not new.html):
Render a section "Publication State" showing current state badge and action buttons. Show ONLY valid transitions per the state machine:
- DRAFT: "Submit for Review" button → POST /api/v1/admin/records/:id/submit-review
- REVIEW: "Publish" button + "Return to Draft" button → POST .../publish and .../return-draft
- PUBLISHED: "Archive" button + "Supersede" button (Supersede opens a modal asking for superseded_by_record_id) → POST .../archive and .../supersede
- SUPERSEDED: "Archive" button → POST .../archive
- ARCHIVED: No action buttons (terminal state — display only)

**Governance gate feedback:**
On failed publish (API returns 422 with { error: 'GOVERNANCE_GATE_FAILED', blockingFields: [...] }):
- Show a visible error section above the form titled "Publication blocked"
- List each blocking field by its human-readable name (derive a human label map: problem_statement → "Problem Statement", owner_name → "Owner Name", source_artifact → "Source Artifact (at least 1 artifact link required)", key_findings → "Key Findings (at least 1 required)", etc.)
- Do NOT dismiss the error automatically; it persists until the user re-attempts publish

**Navigation wiring:**
Add a "Records" nav link in src/views/admin/layout.html pointing to /admin/records (the list page from plan 02-03). Ensure "New Record" button/link is present in the layout's admin nav for CURATOR-role users.

**Record-pages router (src/routes/admin/record-pages.ts):**
```typescript
GET /admin/records/new    → requireAuth + requireRole('CURATOR') → render new.html
GET /admin/records/:id/edit → requireAuth + requireRole('CURATOR') → fetch record from DB via RecordService.getRecord(id, 'CURATOR') → render edit.html with record data
```

Wire recordPagesRouter into src/routes/admin/index.ts:
```typescript

```

Follow the EJS template pattern established in src/views/admin/settings.html (Phase 1). Use the existing admin layout.html as the base. All form submission is handled client-side via fetch (not traditional form POST) so governance gate errors can be rendered without a full page reload.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | EJS edit/new pages submit form data via client-side fetch to /api/v1/admin/records — untrusted curator input crosses into API handlers (handled in 02-01 routes) |
| db→render | Record data fetched from DB is rendered into EJS templates — XSS if output is not escaped |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-08 | Information disclosure | GET /admin/records/:id/edit — page route fetches record from DB and renders into EJS | mitigate | RecordService.getRecord(id, 'CURATOR') applies `WHERE deleted_at IS NULL` scope; if record not found returns null → handler renders 404; EJS uses `<%=` (escaped output) for all user-controlled fields in `src/views/admin/records/edit.html` — prevents stored XSS |
| T-02-09 | Elevation of privilege | GET /admin/records/new and GET /admin/records/:id/edit — EJS page routes | mitigate | requireAuth + requireRole('CURATOR') applied in `src/routes/admin/record-pages.ts` before every handler — unauthenticated → 401 redirect, ADMIN-only or PUBLIC → 403 |
| T-02-10 | Tampering | Supersede modal sends superseded_by_record_id from client — UI-supplied UUID piped into POST .../supersede body | mitigate | Route handler in `src/routes/admin/records.ts::supersede` validates that superseded_by_record_id is a valid UUID format and that the referenced record exists before calling PublicationLifecycleService.transition(); Knex parameterized query prevents SQL injection |
| T-02-11 | Information disclosure | blockingFields array from governance gate rendered into DOM — could be used to probe DB state | accept | blockingFields contain only field names (static strings from GovernanceGateService), never DB row data or internal identifiers. Accepted: no sensitive data exposed; curator-only route already requires auth. |
</threat_model>
